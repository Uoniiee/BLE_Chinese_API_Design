## A-side Findings

1. A-side business send does not block behind stale client writes in v0.6.3. The notification path returns in 1-3 ms, and `[SEND#] result=success` returns in 3-4 ms for normal sends.

2. Background client writes are noisy. `write-bg peer=0708 result=failed(写入失败:1)` appears several times after the main notification path already succeeded. This is not fatal for the business send, but it can confuse diagnostics. For production API behavior, consider whether background write after successful notification should be disabled, hidden behind debug logging, or used only for cleanup.

3. One physical peer can appear as two logical channels. During a server-side disconnect, A drops from `connected=2 writable=2` to `connected=1 writable=1`, not to zero, because the client write path remains. Business UI should not decide "opponent is fully connected" only from a non-zero logical channel count.

4. The reconnect path does recover. In the visible A logs, the channel returns to `connected=2 writable=2` after about 4.5-6.3 seconds.

5. A-side evidence alone cannot prove whether received `T1/T3/T4/T5/T6/T8/T9` messages are expected C-side sends or accidental self-echo. This needs C-side log comparison.

## Interim Conclusion

For A / Honor 50 Pro, v0.6.3 reaches the diagnostic goal of exposing the real transport behavior:

- notification-first sending is fast and stable;
- stale or failing client write paths no longer block the business send;
- disconnect/reconnect is visible in `[PEERS]` and recovers;
- the remaining design question is how the Chinese API should expose a merged physical-peer state instead of raw logical channel counts.

Wait for C / Redmi Note 9 logs before deciding whether the minimal diagnostic result can be merged into the public Chinese API behavior.
