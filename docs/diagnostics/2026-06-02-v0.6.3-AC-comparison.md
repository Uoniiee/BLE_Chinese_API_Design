# BLE Chinese API v0.6.3 A/C Comparison

Date: 2026-06-02

Devices:

- A: Honor 50 Pro / Android 14 / stable id `310668f1`
- C: Redmi Note 9 / Android 12 / stable id `fbb20708`

Purpose: compare A-side and C-side screenshot logs from the same v0.6.3-debug diagnostic run.

## What The Logs Prove

### 1. Stop And Restart Cleanup Works Locally

C active stop:

- C log repeatedly shows `[APP] stop-done`, then `[PEERS] connected=0 writable=0 peers=empty`, then `[STATE] 未启动`.
- This means active stop on C cleans local BLE state promptly.

A observes C disconnect later:

- A sees server-side peer disconnect events after C has stopped.
- A drops from `connected=2 writable=2` to `connected=1 writable=1`.

Interpretation: Android reports the remote disconnect to the other phone with a delay. During that delay, A may still believe one logical path is usable.

### 2. Reconnect Works, But There Is A Not-Ready Window

C restart flow often passes through:

- `connected=1 writable=0 clients=0 subscribed=0`
- then notification/write setup
- then `connected=1 writable=1 clients=1 subscribed=0`

C sends during the not-ready window:

- C `T2`: failed quickly because no subscribed notification and no client write path.
- C `T7`: failed quickly for the same reason.

Interpretation: the API is correctly reporting failure when no writable path exists, but the sample/game UI should not enable send while the peer is still in this not-ready state.

### 3. Notification Success Is Not Delivery Confirmation

A sends while C is stopped or not fully ready:

- A `T2`: A reported notification success, but C had stopped and no C receive line is visible.
- A `T5`: A reported notification success, but C was stopping/restarting and no C receive line is visible.
- A `T7`: A reported notification success shortly before A observed server-side disconnect; C was stopped and no receive line is visible.
- A `T10`: A reported notification success while C was stopped before the next restart; no C receive line is visible.

Interpretation: `BluetoothGattServer.notifyCharacteristicChanged` returning success means Android accepted the notification request. It does not guarantee the remote app actually received the message.

### 4. Client Write Path Is Slower But More Observable

C sends after writable setup:

- C `T3`, `T4`, `T5`, `T6`, `T8`, `T9` all succeed through `write peer=68f1`.
- Typical result time is about 104-155 ms.
- C has `subscribed=0`, so it cannot use notification-first sending in these windows.

A receives these C messages:

- A receives C `T3`, `T4`, `T5`, `T6`, `T8`, `T9`.

Interpretation: C-to-A delivery is working through GATT client write even when notification is unavailable from C's perspective.

### 5. Logical Channel Counts Are Asymmetric

A commonly shows:

- `connected=2 writable=2`
- or after remote stop, `connected=1 writable=1`

C commonly shows after reconnect:

- `connected=1 writable=1`

Interpretation: the raw channel count is a BLE topology/debug value, not a business-level "opponent is ready" value. The Chinese API should provide a merged physical-peer readiness concept for business apps.

## Recommended Next Design Direction

For the Chinese API:

1. Keep v0.6.3 diagnostic behavior as evidence, but do not treat `发送结果.已写入` as delivery confirmation.

2. Add a business-facing peer readiness state that merges logical channels by stable peer id:
   - not started
   - searching
   - connecting
   - connected but not writable
   - ready/writable
   - recently disconnected / cooling down

3. The sample and future RPS integration should enable send only when the selected peer is in `ready/writable`.

4. If game/message delivery must be exact, add an application-level ack:
   - sender includes message id;
   - receiver sends ack after parsing;
   - sender treats the message as delivered only after ack;
   - request-level BLE success remains only "write/notify accepted".

5. Keep diagnostic counters visible in debug builds, but avoid exposing raw `connected=2 writable=2` as the main UI truth for business apps.

## Acceptance For The Minimum Diagnostic APK

v0.6.3 achieved the diagnostic goal:

- it reveals the delay between active stop and remote disconnect observation;
- it reveals the not-ready reconnect window;
- it shows notification-first sending avoids stale write blocking;
- it shows notification success can still lose a message if the remote app has already stopped;
- it shows repeated stop/start does not make local peer records grow indefinitely.

The next version should not be another blind patch. It should implement a merged peer readiness model and, if needed, a small ack protocol for delivery-critical messages.
