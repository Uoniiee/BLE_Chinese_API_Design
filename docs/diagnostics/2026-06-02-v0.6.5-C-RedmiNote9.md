## Summary

This C-side log confirms that v0.6.5 keeps business readiness at `ready=0` after the peer disconnects, even when stale physical GATT channels later still appear as connected/writable. Based on this C-side log and the matching A-side log, no immediate v0.6.6 code change is required for the current disconnect/reconnect acceptance target.

## Findings

1. Remote disconnect guard is effective.
   After A disconnects at 14:10:06, C records a business disconnect for peer `0d11` and reports `ready=0`. Later stale physical channel output does not restore business readiness.

2. Send gating works.
   C attempts at 14:10:36 and 14:11:45 are skipped with `peer_not_ready`. This is the intended behavior after a peer disconnects.

3. Manual local stop is clean.
   When C taps stop at 14:05:57, C clears all peers and readiness immediately. There is no C-side evidence of readiness returning before the later manual start at 14:09:07.

4. Reconnect recovery works.
   After A reconnects at 14:11:53 - 14:11:54, C returns to `ready=1` and can send/receive normally.

5. Notification and direct write are independent paths.
   Some successful direct-write sends appear while `subscribed=0`. This is acceptable in the current transport model because notify is the local server-to-peer-client path, while direct write is the local client-to-peer-server path.

## Decision

The v0.6.5-debug behavior matches the current acceptance target:

- disconnected peer does not become business-ready due to stale physical channel state;
- send attempts are blocked while the peer is not business-ready;
- reconnect restores readiness;
- local stop clears local state cleanly.

Keep v0.6.5 as the current candidate. If future logs show readiness returning without a manual start or real reconnect, the next defensive step should be a session/generation guard, but this C-side log does not currently prove that issue.
