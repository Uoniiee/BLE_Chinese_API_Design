## C-side Findings

1. Active stop clears C immediately. In every visible stop cycle, C goes to `connected=0 writable=0 peers=empty` and `STATE 未启动`.

2. Restart is not instant. C often enters `connected=1 writable=0` first, then reaches `connected=1 writable=1` after notification subscription/write characteristic setup. The gap is usually under one second, but the user can still tap "短测" inside that gap.

3. Send attempts during the `writable=0 clients=0 subscribed=0` gap fail quickly and correctly. This happened for C `T2` and `T7`.

4. After C reaches `writable=1 clients=1 subscribed=0`, C can send successfully through the client write path. The send time is roughly 113-158 ms, slower than A's notification-first path but stable.

5. C normally reports one logical channel after later reconnects, while A often reports two. This confirms that raw logical channel counts are asymmetric and should not be exposed directly as "physical opponent connected" state in a game UI.

6. A messages sent while C is stopped can still appear as `success` on A because A's notification request can return success before Android reports the remote disconnect. That is not delivery confirmation.

## Interim Conclusion

For C / Redmi Note 9, v0.6.3 exposes the main remaining design issue:

- stop/start cleanup itself is stable;
- reconnect eventually succeeds;
- the unsafe window is "connected but not yet writable";
- notification success is not a delivery ack;
- business apps should wait for a merged physical-peer-ready state before enabling send, and should use an app-level ack when delivery must be guaranteed.
