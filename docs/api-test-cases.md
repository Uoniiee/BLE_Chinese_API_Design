# BLE 中文 API 测试说明与用例

本文档用于说明当前 `issue-1-reliable-transport` 分支上 BLE 中文 API 的
关键行为，以及 sample app 对这些行为的测试方式。

当前测试包：`v0.6.7-debug`

## 范围

本测试说明聚焦 BLE 中文 API 本身，不覆盖 BBS 帖子同步、长帖分片、
历史消息补同步、账号权限或业务 UI。

当前 API 主要验证以下能力：

- 启动与停止 BLE 通信。
- 发现、连接和订阅附近设备。
- 通过 `对手状态流` 提供业务可用的 `可发送` 判断。
- 发送和接收短消息。
- 去重已经处理过的消息。
- 对端断开后，不把旧 BLE 通道误判为业务可发送。
- 本机停止后，旧 scan/GATT 回调不会恢复旧状态。
- 导出诊断日志，方便按时间线排查问题。

## 状态说明

sample app 会同时显示底层通道状态和业务就绪状态：

- `[PEERS] connected=... writable=...`
  表示底层 BLE 逻辑通道。它可能包含扫描记录、服务端连接、客户端连接和
  通知订阅记录，不一定等于物理手机数量。
- `[READY] ready=... total=...`
  表示按稳定设备 ID 归并后的业务对手状态。业务 App 应优先依据这里判断
  是否允许发送。
- `可发送`
  表示当前有可用发送路径，业务 UI 可以允许发送。
- `连接中`
  表示已发现或已连接，但通知订阅/写入路径尚未稳定完成。
- `刚断开`
  表示同一业务对手最近发生断开，业务 UI 应回到等待或寻找状态。
- `忽略过期回调`
  表示旧通信会话的 scan/GATT 回调晚到，已被会话保护拦截。

日志中的 `[APP]`、`[STATE]`、`[PEERS]`、`[READY]`、`[API]`、`[RECV]`
是稳定调试标签，方便代码、测试记录和双端日志互相对应。

## 测试准备

1. 至少准备两台 Android 设备。
2. 两台设备都安装同一个版本的 sample app，例如 `v0.6.7-debug`。
3. 开启蓝牙。
4. 允许附近设备、蓝牙扫描/广播/连接和定位相关权限。
5. 如果系统要求定位服务，保持定位服务开启。
6. 测试前确认日志顶部显示的版本号一致。

## 用例 1：启动与发现

目的：确认两台设备可以启动 BLE 通信，并发现对方。

步骤：

1. A、C 两台设备打开 sample app。
2. 两台设备都点击“启动通信”。
3. 等待 1 到 5 秒。

预期结果：

- 两端出现 `[APP] start-result=成功`。
- 两端状态进入 `[STATE] 扫描广播中` 或 `[STATE] 已连接`。
- 至少一端出现 `[READY] ready=0 total=1 ... 已发现` 或
  `[READY] ready=0 total=1 ... 连接中`。

## 用例 2：两机双向短消息

目的：确认两台设备建立可发送状态后可以双向收发短消息。

步骤：

1. 继续用例 1。
2. 等待两端至少一端显示 `[READY] ready=1 ... 可发送`。
3. A 点击“短测”。
4. C 点击“短测”。

预期结果：

- 发送端出现 `send-result=success`。
- 接收端出现 `[RECV] T...`。
- 发送日志中可出现 `notify=success` 或 `write ... result=success`。
- 如果 `subscribed=0` 但 direct write 成功，仍属于当前 API 允许的成功路径。

## 用例 3：对端停止通信

目的：确认一台设备停止通信后，另一台设备不会继续误判对端为可发送。

步骤：

1. A/C 已经进入可发送状态。
2. A 点击“停止通信”。
3. C 观察日志。
4. C 点击“短测”。

预期结果：

- A 立即显示：
  - `connected=0 writable=0 peers=empty`
  - `ready=0 total=0 peers=empty`
  - `[STATE] 未启动`
- C 可短暂看到底层 `connected=1 writable=1`，但业务状态应进入：
  - `[READY] ready=0 ... 刚断开`
- C 点击“短测”时应出现：
  - `send-skip reason=peer_not_ready`

已验证记录：

- `v0.6.7-debug` A/C 两机导出日志已验证此行为。
- 记录见 `docs/diagnostics/2026-06-02-v0.6.7-AC-log-export-analysis.md`。

## 用例 4：本机停止后的旧回调保护

目的：确认本机停止通信后，旧 scan/GATT 回调晚到也不会恢复旧状态。

步骤：

1. A/C 已经进入可发送状态。
2. C 点击“停止通信”。
3. C 观察后续日志。

预期结果：

- C 立即显示：
  - `connected=0 writable=0 peers=empty`
  - `ready=0 total=0 peers=empty`
  - `[STATE] 未启动`
- 如果旧回调晚到，应看到类似：
  - `忽略过期回调：scan-result，会话=...，当前=...`
- 出现“忽略过期回调”后，不应重新出现 `ready=1`，除非用户之后再次点击
  “启动通信”。

已验证记录：

- `v0.6.7-debug` C 机导出日志中已出现 `忽略过期回调`，且状态未被污染。

## 用例 5：手动重新启动恢复通信

目的：确认停止后手动启动，可以重新连接并恢复发送。

步骤：

1. 继续用例 3 或用例 4。
2. 停止过的设备再次点击“启动通信”。
3. 等待两端恢复 `[READY] ready=1 ... 可发送`。
4. A/C 分别点击“短测”。

预期结果：

- 两端重新出现 `ready=1`。
- 双方短消息发送成功。
- 不应依赖旧会话回调恢复状态，日志中应有新的 `start-click` 和新的会话编号。

## 用例 6：连发与去重

目的：确认连续发送时不会因为写入队列或中继去重出现明显异常。

步骤：

1. A/C 已经进入可发送状态。
2. A 点击“连发5次”。
3. C 点击“连发5次”。
4. 观察双方日志。

预期结果：

- 发送端多次出现 `send-result=success`。
- 接收端出现对应 `[RECV] B...`。
- 不应出现自己收到自己消息的重复显示。
- 不应出现连续发送后状态异常变成 `ready=0`，除非实际发生断开。

## 用例 7：导出日志

目的：确认测试后可以一键导出日志，便于复查。

步骤：

1. 完成任意测试流程。
2. 点击“保存日记”。
3. 在系统文件管理或 Downloads 目录中查找 txt 日志。

预期结果：

- sample app 日志出现 `[APP] save-log-click`。
- 成功时出现 `[APP] save-log-success file=...`。
- 导出的 txt 包含：
  - 版本号。
  - 保存时间。
  - 设备型号。
  - Android 版本。
  - 连续 `[APP]`、`[STATE]`、`[PEERS]`、`[READY]`、`[API]`、`[RECV]`
    日志。

已验证记录：

- `v0.6.7-debug` A/C 两机均已成功导出日志。

## 三机回归用例

三机通信是 `v0.6.1-debug` 已验收过的历史能力。`v0.6.7-debug` 本轮重点
验证的是两机断开、重连、旧回调保护和日志导出。

如果需要对新版做三机回归，可按以下步骤复测：

1. A/B/C 三台设备都安装同一版本。
2. A/B 先启动通信并互发短消息。
3. C 再启动通信。
4. A/B/C 分别发送短消息。
5. 其他两台设备应能收到消息。
6. 任意一台设备停止通信，其余设备不应出现错误 `ready=1`。
7. 停止设备再次启动后，三台设备恢复短消息互通。
8. 三台设备分别保存日志，用于对齐分析。

说明：

- 该用例用于回归当前 API 的多设备基础互通，不等同于完整 BBS 历史消息同步。
- BBS 业务同步、长帖分片和断线后补同步应作为业务层用例另行设计。

## 当前 v0.6.7 测试结论

`v0.6.7-debug` 已用 A/C 两台 Android 真机验证：

- 两机可启动并进入可发送状态。
- 两机可双向发送短消息。
- 对端停止后，业务 `ready` 不会被旧底层通道误恢复。
- 本机停止后，旧 scan/GATT 回调会被会话保护拦截。
- 手动重新启动后可以恢复连接和发送。
- 连发测试通过。
- 日志可以一键导出为可读 txt 文件。

历史记录中，`v0.6.1-debug` 已通过三机最小互通测试；如需把 `v0.6.7-debug`
作为后续项目基线，建议在正式进入新业务前再做一次三机回归。
